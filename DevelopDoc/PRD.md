# PRD — Task Insight

작성일: 2026-11-25 · 근거: [README](../README.md), [CLAUDE.md](../CLAUDE.md), [docs/data_rules.md](../docs/data_rules.md) · 상태: **초안 — 제출 전 최종 점검에서 갱신**

## 1. 배경과 문제

- 업무·직원·프로젝트 데이터는 보통 CSV로 따로 관리되고, 팀장·PM은 "기한이 지난 업무가 몇 건인가", "예산을 넘긴 프로젝트는 어디인가" 같은 질문을 엑셀 피벗으로 직접 푼다.
- 일반적인 "CSV 올리면 AI가 답하는" 도구는 두 가지 위험이 있다.
  1. **조인 부풀림**: 업무 표에 프로젝트 예산을 붙여 합하면 프로젝트당 업무 수만큼 중복된다. (시연 데이터: 7.03억 → 109.03억 원, 15.5배)
  2. **LLM 환각**: LLM이 계산하면 그럴듯하지만 근거 없는 숫자가 나온다.
- 결측(담당자·기한 빈칸)을 오류로 오해하거나, 누적 실적 MH를 주당 가용시간과 비교해 과부하로 판단하는 해석 오류도 흔하다.

## 2. 목표

| # | 목표 | 측정 |
|---|---|---|
| G1 | 질문에 **정확한 숫자와 근거**로 답한다 | 평가 질문 Q1~Q7, sample.csv S1~S5가 고정 정답과 일치 |
| G2 | 사용자가 **무엇을 계산할지 먼저 보고 승인**한다 | 승인 전 도구 실행 0회 |
| G3 | 데이터 오류와 한계를 **숨기지 않고 알린다** | 오류 샘플 8종 거부·경고, 미지원 질문은 숫자 없이 거절 |
| G4 | 처음 보는 CSV에도 동작한다 | 다른 업종 데이터 3종 질문 묶음(general·holdout) |

## 3. 사용자

- **주 사용자**: 개발 지식이 없는 팀장·PM·경영지원 담당자. 엑셀은 쓰지만 조인·피벗 오류를 직접 잡기는 어렵다.
- **발표 청중(해커톤 심사)**: 정확성 가드레일과 승인 흐름을 확인한다.

## 4. 범위

### 포함 (과제 Step 1 + Step 3)
- CSV 업로드와 파일별 검증, 표준 3종(업무·직원·프로젝트) 자동 결합, 일반 CSV 분석
- 질문 → 분석 계획 → 승인 → 실행 → 실행 기록
- 분석 도구 10개, 표·차트·근거·설명문
- 시연 데이터 kafe, 발표용 소개 홈페이지, Streamlit Community Cloud 배포

### 제외
- 로그인, 분석 결과 저장 (Step 2, 의도적 제외)
- 자유 Python/SQL 실행
- 원인 추정, 위험도 판단, 완료 시점·비용 예측
- 주차별 과부하 분석 (시간 기록 데이터 없음), 주·분기 단위 비교
- 표준 3개 표 외 파일 결합, 업무명 등 자유 텍스트 의미 분석

## 5. 핵심 사용자 흐름

1. 예시 데이터를 고르거나 CSV를 올린다 → 파일별 검증 결과와 결합 전후 행 수를 본다.
2. 질문을 입력한다 (예: "기한이 지난 미완료 업무는 몇 건인가?").
3. AI가 만든 **분석 계획**(단계, 목적, 도구, 조건)을 확인한다. 지원하지 않는 질문이면 이유와 함께 안내받는다.
4. [승인하고 실행]을 누른다. 계획이 바뀌면 다시 승인해야 한다.
5. 표·차트·기준·단위·설명문을 본다. 계산할 수 없으면 숫자 대신 사유를 본다.
6. 실행 기록(어떤 도구를 어떤 인자로 실행했는지)을 확인한다.

## 6. 기능 요구사항

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-1 | 파일 종류(업무·직원·프로젝트·일반)를 컬럼으로 자동 인식한다 | 필수 |
| FR-2 | 빈 파일, 10MB·10만 행 초과, 인코딩 오류, 필수 컬럼 누락은 거부하고 이유를 알린다 | 필수 |
| FR-3 | 형식 오류 행은 행 번호와 함께 경고하고 계산에서 제외한다 | 필수 |
| FR-4 | 담당자·기한 빈칸은 오류가 아니라 "확인 필요"로 표시한다. 구조적 공백(미완료 업무의 완료일 등)은 정상으로 본다 | 필수 |
| FR-5 | 업무 → 직원·프로젝트를 다대일로 결합하고, 결합 후 행 수가 달라지면 결과를 쓰지 않는다. 예산은 업무 행에 붙이지 않는다 | 필수 |
| FR-6 | 질문을 분석 계획(최대 4단계)으로 바꾼다. 질문의 조건이 계획에 반영되지 않으면 해당 단계를 승인 대상에서 뺀다 | 필수 |
| FR-7 | 승인 전에는 어떤 도구도 실행하지 않는다 | 필수 |
| FR-8 | 허용된 도구 10개만 실행한다 | 필수 |
| FR-9 | 결과의 모든 숫자는 `ToolResult`에서 가져오고, 차트와 표는 같은 `rows`로 그린다. 기준·단위를 함께 표시한다 | 필수 |
| FR-10 | `ToolResult.error`가 있으면 숫자를 보여주지 않는다. LLM 호출이 실패하면 "실패"를 표시한다 | 필수 |
| FR-11 | 데이터에 없는 컬럼·지표를 묻거나 미지원 분석이면 다른 분석으로 대체하지 않고 거절한다 | 필수 |
| FR-12 | 날짜 계산은 기준일(`as_of`)을 입력으로 받는다 | 필수 |
| FR-13 | 업무명·프로젝트명 등 자유 텍스트를 LLM 프롬프트에 넣지 않는다 | 필수 |
| FR-14 | 일반 CSV의 구분자, 날짜·숫자 표기(`2026/01/05`, `₩1,200`, `12.5%`)를 자동 정리한다 | 권장 |
| FR-15 | 발표용 소개 홈페이지에서 배포 앱을 열어 시연한다 | 권장 |

## 8. 성공 기준

- `pytest` 전체 통과
- kafe Q1~Q7과 sample.csv S1~S5가 정답과 일치
- 발표 시연 질문 5개(`eval --set demo`)가 에이전트로 정답
- 미지원·누락 컬럼 질문은 숫자 없이 거절

## 9. 가정과 한계

- 인건비는 현재 직원 단가를 소급 적용한 **추정액**이다.
- 비용 초과율은 기준일 **누적값**이며 완료 시점 예측(EAC)이 아니다.
- 실적 MH는 누적값이라 주당 가용시간과 비교하지 않는다.
- Gemini API는 무료 한도와 503·504 오류가 있을 수 있어 호출 실패 시 안내를 표시한다.
- 시연 데이터는 가상이며 실제 업무 성과를 대표하지 않는다.

## 11. 초기 기획 (프로젝트 시작 시점, 팀장 정리)

> 시작 때 정리한 기획안을 근거로 한 내용이다. 기획안과 결과물의 비교는 `docs/initial_plan_review.md`(PR #56)에 있다. 이 PRD는 최종 결과물 기준이며, 달라진 부분은 TECH_SPEC 12절에 적었다.

### 11.1 제안한 모습
- 입력은 엑셀·CSV와 자연어 질문, 출력은 현황 요약, 주요 문제, 시각화, 후속 확인사항.
- 핵심은 사용자가 복잡한 그래프를 일일이 해석하지 않도록 **AI가 중요한 변화와 그 근거를 먼저 제시**하는 것.
- 같은 분석 엔진에 데이터만 바꿔 쓴다. 예: 안전관리자 "어느 구역에서 개선조치가 반복 지연되는가?", 품질관리자 "어느 공정의 불량 개선조치가 오래 걸리는가?", 시설관리자 "어떤 설비의 수리가 반복되는가?"
- 기획 단계의 가칭은 "Action Insight AI", 최종 이름은 Task Insight.

### 11.2 넣어야 할 데이터
업무 내용을 표준화하는 것이 아니라 **업무 관리에 필요한 공통 항목만 정의**한다. 기획 단계 항목: ID, 분야, 업무 및 문제, 담당부서, 등록일, 기한, 상태 (구현에서는 발생일·완료일, 업무 유형, 반복 문제 식별 정보까지 정의하는 것을 권장).
계산하려던 것:
- 기한이 지난 미완료 업무는 몇 건인가?
- 담당부서별 처리율에 차이가 있는가?
- 어느 유형의 문제가 반복되는가?
- 처리기간이 늘어나고 있는가?
- 어떤 업무에 추가 확인이 필요한가?

'우선 확인'은 기한 초과, 반복 발생, 사용자 지정 중요도 같은 근거로 제시하고, **AI가 문제의 위험도를 자의적으로 확정하지 않는다.**

### 11.3 시각화 원칙
차트를 나열하지 않고 **하나의 핵심 질문에서 시작**한다 (예: "이번 달에 가장 먼저 확인할 문제는?" → 부서별 기한 초과 막대 → 권장 확인사항). 이 정도만으로도 "엑셀 업로드 → 질문 → 그래프·설명 확인"의 완성된 흐름이 된다. 업무관리 데이터만으로는 지연의 원인을 알 수 없으므로 원인까지 단정하지 않는다.

### 11.4 에이전트가 할 일
데이터를 LLM에 통째로 전달하지 않는다. **LLM이 분석 방법을 정하고, Python이 계산하고, 결과를 설명한다.** 처음부터 여러 에이전트를 만들지 않고 **단일 LLM + 4~5개 분석 도구 + 명시적 검증 로직**으로 시작한다 (예: `count_overdue_tasks`, `summarize_by_category`, `calculate_completion_rate`, `compare_periods`, `find_recurring_issues`).

### 11.5 각자에게 남는 기술적 자산
| 해커톤 개발 결과 | 업무 활용 |
|---|---|
| CSV/DB 분석 파이프라인 | 안전점검, TBM, 개선조치 데이터 |
| 자연어 질문의 구조화 | 관리자의 자연어 데이터 조회 |
| 계산 도구 호출 | 개선조치 기한, 위험유형별 집계 |
| 데이터 근거 검증 | AI의 숫자 생성·사실 왜곡 방지 |
| 대시보드 시각화 | 사업장 현황, 보고서, PDCA 성과 |
| 보고서 생성 | 안전보건 월간 실적보고 |

핵심 자산은 **자연어 질의를 검증 가능한 데이터 조회와 계산으로 바꾸는 에이전트 구조**다.

### 11.6 최종 제안 (당시)
- 주제: AI 기반 업무 현황 진단 및 개선 우선순위 분석 에이전트
- 핵심 고객: 데이터를 기반으로 업무 현황을 관리하는 실무자와 관리자
- 입력: 업무 관리 CSV/엑셀 + 자연어 질문
- 출력: 현황 요약, 문제 및 지연 분석, 그래프, 근거와 후속 확인사항
- 개발 범위: 5개 내외 분석 도구, 공통 데이터 구조 1개, 검증 가능한 질문 10~20개
- 단서: "어떤 엑셀이든 AI가 알아서 분석한다"는 약속은 하지 않는다. 지원하는 컬럼과 지표를 명확히 정해야 완성도와 신뢰성을 확보한다.
- 평가 아이디어: 엑셀 피벗이나 미리 구성한 대시보드와 비교해 사용자가 정보를 얻는 **단계 수와 정확성**을 평가한다 (결과: 정확성은 평가, 단계 수 정량 비교는 미수행).
