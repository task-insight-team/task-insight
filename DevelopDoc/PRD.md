## 1. 개요

업무·직원·프로젝트 CSV를 올리고 질문하면, AI가 분석 계획을 세우고 사용자가 승인한 뒤 검증된 계산 도구를 실행해 표·차트·근거로 답하는 웹 도구.

한 줄 정의: **"숫자는 계산 도구가 만들고, AI는 무엇을 계산할지만 고르는" 업무 데이터 분석 에이전트.**

---

## 2. 문제 정의

업무 데이터는 보통 CSV로 따로 관리된다. 팀장·PM은 "기한이 지난 업무가 몇 건인가", "예산을 넘긴 프로젝트는 어디인가" 같은 질문을 엑셀 피벗으로 직접 푼다. 이를 AI에게 맡기는 도구는 두 부류로 갈린다.

| 유형 | 문제점 |
|---|---|
| 엑셀 피벗 직접 작업 | 표를 결합하고 피벗을 만드는 과정에서 조인 부풀림, 결측 오해가 생기기 쉽고 사람마다 결과가 다름 |
| "CSV 올리면 AI가 답하는" 도구 | LLM이 직접 계산하면 그럴듯하지만 근거 없는 숫자가 나오고, 무엇을 계산했는지 사용자가 확인할 수 없음 |

대표 사례: 업무 표에 프로젝트 예산을 붙여 합하면 프로젝트당 업무 수만큼 중복되어, 실제 예산 합계 7.03억 원이 109.03억 원(15.5배)으로 부풀려진다. 담당자·기한 빈칸을 오류로 오해하거나, 누적 실적 MH를 주당 가용시간과 비교해 과부하로 판단하는 해석 오류도 흔하다.

공통적으로 **"이 숫자가 어떻게 나왔는지"를 보여주지 않는다.** 사용자는 결과만 받고 검증할 방법이 없다.

### 우리의 접근

1. **계산은 결정론적으로, 투명하게.** 허용된 도구 10개만 실행하고, 결과의 모든 숫자는 `ToolResult`에서 가져온다. 기준(basis)과 단위(unit)를 함께 표시한다.
2. **AI는 도구와 조건만 고른다.** 사용자는 실행 전에 계획(계산식, 조건)을 보고 승인한다. 승인 후 계획이 바뀌면 다시 승인을 받는다.
3. **모르는 것은 모른다고 한다.** 데이터에 없는 컬럼·지표나 지원하지 않는 분석은 다른 분석으로 바꿔 답하지 않고 거절한다.

## 3. 목표 / 비목표

### 3.1 MVP 목표

| # | 목표 | 측정 방법 |
|---|---|---|
| G1 | 질문에 정확한 숫자와 근거로 답한다 | 평가 질문 Q1~Q7, sample.csv S1~S5가 고정 정답과 일치 (테스트 + pandas 별도 재계산) |
| G2 | 사용자가 계산 내용을 먼저 보고 승인한다 | 승인 전 도구 실행 0회 (테스트로 확인) |
| G3 | 데이터 오류와 한계를 숨기지 않는다 | 오류 샘플 8종 거부·경고, 미지원 질문은 숫자 없이 거절 |
| G4 | 처음 보는 CSV에도 동작한다 | 다른 업종 CSV 질문 묶음(`general`, `holdout`, `schema`)에서 정답 또는 정직한 거절 |

### 3.2 MVP 비목표 (명시적으로 하지 않는 것)

- 로그인, 분석 결과 저장 (과제 Step 2, 의도적 제외)
- 자유 Python/SQL 실행
- 원인 추정, 위험도 판단, 완료 시점·비용 예측
- 주차별 과부하 분석 (시간 기록 데이터 없음), 주·분기 단위 비교
- 표준 3개 표 외 파일 결합, 업무명 등 자유 텍스트의 의미 분석
- 모바일 네이티브 앱, 다국어 지원 (한국어 단일)

## 4. 대상 사용자

### 페르소나 A — "엑셀로 현황을 보는 팀장·PM" (주 타깃)

- 업무·직원·프로젝트 데이터로 팀 현황을 관리하고, 엑셀은 쓰지만 조인·피벗 오류를 직접 잡기는 어려움
- 니즈: 질문 한 줄로 근거가 있는 답, 무엇을 계산했는지 확인 가능
- 이탈 요인: 그럴듯하지만 틀린 숫자, 설명 없는 결과

### 페르소나 B — "결과를 검증하는 사람" (품질 검증자)

- 데이터 담당자, 해커톤 심사위원처럼 정답과 계산 기준을 확인하려는 사람
- 니즈: 정답과 일치하는가, 어떤 도구와 인자로 계산했는가, 한계를 솔직히 밝히는가
- 이탈 요인: 틀린 숫자 1건, 지원하지 않는 질문에 엉뚱한 분석으로 답하는 것

> **설계 원칙:** A를 위해 만들되, B의 검증을 통과해야 한다. 계산 정확도는 타협 대상이 아니다.

## 6. 기능 요구사항

### 6.1 P0 — MVP 필수

#### F-01. 업로드와 검증
- 파일 종류(업무·직원·프로젝트·일반 CSV)를 컬럼으로 자동 인식 (ID 컬럼이 있고 해당 표 컬럼의 절반 이상이 있어야 표준 파일)
- 거부: 빈 파일, 헤더만 있음, 10MB·10만 행 초과, UTF-8·CP949 아님, 같은 헤더 중복·`_` 시작 헤더, 표준 파일의 필수 컬럼 누락
- 경고 + 행 번호 + 계산 제외: 필수값 빈칸, 날짜·숫자·허용값 오류, 음수
- 경고 + 값 유지: 담당자·기한 빈칸은 '확인 필요'(담당자 빈칸의 부서는 '미배정'). 미완료 업무의 완료일 등 구조적 공백은 정상
- 완전 중복 행은 사용자가 확인하면 첫 행만 남기고 제거
- 원본 파일과 DataFrame을 수정하지 않음

#### F-02. 결합
- 업무 → 직원(`assignee_id`), 업무 → 프로젝트(`project_id`) 다대일 결합. 업무의 부서는 담당자의 부서
- 결합 후 행 수가 업무 행 수와 같아야 하며, 다르면 결합 결과를 쓰지 않음. 직원·프로젝트 표에 ID 중복이 있으면 결합하지 않음
- **예산은 업무 행에 붙이지 않음** (프로젝트 표에서 프로젝트당 한 번만 사용)

#### F-03. 분석 계획 생성
- 질문을 독립인 단계 최대 4개의 계획(목적, 도구, 인자, 차트 종류)으로 변환 (Gemini function calling)
- LLM에는 컬럼 이름, 형식, 범주값, ID 목록, 기준일만 보냄. 업무명·프로젝트명 같은 자유 텍스트와 숫자 값은 보내지 않음
- 질문의 조건(부서·프로젝트·직원·상태·기한·기간·지표)이 계획에 반영되지 않으면 그 단계를 승인 대상에서 빼고 1회 재계획, 그래도 안 되면 지원 불가로 안내

#### F-04. 승인과 실행
- 승인 전에는 어떤 도구도 실행하지 않음
- 승인 후 인자가 하나라도 바뀌면 실행하지 않고 재승인 요구 (계획 지문 `plan_hash`)
- 도구는 `engine.run_tool`로만 실행. 허용 목록(10개) 밖의 도구, 자유 Python/SQL 실행 금지

#### F-05. 분석 도구 10개
집계(`aggregate`), 비율(`calculate_ratio`), 기간 비교(`compare_periods`), 기한 초과(`count_overdue_tasks`), 범주별 요약(`summarize_by_category`), 완료율(`calculate_completion_rate`), 반복 문제(`find_recurring_issues`), MH 초과(`mh_overrun`), 예산 대비 비용(`cost_vs_budget`), 누락 데이터(`check_missing_data`). 인자·계산 기준은 [docs/data_rules.md](../docs/data_rules.md).
- 날짜 계산은 기준일(`as_of`)을 입력으로 받음. 코드에서 오늘 날짜를 쓰지 않음

#### F-06. 결과 표시
- 표와 차트는 같은 `ToolResult.rows`로 그림. 결과 옆에 기준·단위, 설명문, 실행 기록 표시
- 설명문은 Python 템플릿이 만들며 LLM을 쓰지 않음. 숫자는 모두 `ToolResult`에서 가져옴
- `ToolResult.error`가 있으면 숫자를 보여주지 않고 사유를 보여줌. LLM 호출이 실패해도 가짜 답 대신 "실패"를 표시

#### F-07. 한계 안내 (사전 차단·사후 검증)
- 데이터에 없는 개념·컬럼, 지원하지 않는 계산(원인 추정, 예측, 주차별 과부하 등)은 LLM 호출 전에 "지원 불가" 또는 되묻기
- 다른 분석으로 바꿔 답하지 않음. 숫자 없이 끝남

### 6.2 P1 — 보강

- F-08. 일반 CSV 정리: 구분자 자동 인식, 날짜·숫자 표기 정리(`2026/01/05`, `₩1,200`, `12.5%`), 형식 오류는 그 칸만 제외
- F-09. 발표용 소개 홈페이지(정적 페이지)와 배포: 분석 앱(Streamlit Community Cloud)을 iframe으로 포함, 홈페이지는 Netlify
- F-10. 컬럼 의미 해석: 질문 용어와 컬럼 이름이 다를 때 후보를 찾는 기능. 기능 스위치 `TI_COLUMN_HINTS`, **기본 OFF**, 발표에서는 켜지 않음

### 6.3 P2 — 향후

- 파일을 올리자마자 문제를 먼저 알려 주는 능동 리스크 브리핑
- 앞 결과에 따라 인자가 바뀌는 질문(결과 간 연결)
- 질문 용어와 컬럼 이름을 사용자가 확인하는 스키마 매핑
- 로그인과 결과 저장 (Step 2)
- 엑셀 대비 단계 수 정량 비교

## 부록 A. 초기 기획 (프로젝트 시작 시점, 팀장 정리)

> 시작 때 정리한 기획안을 근거로 한 내용이다. 기획안과 결과물의 비교는 [docs/initial_plan_review.md](../docs/initial_plan_review.md)에 있다. 이 PRD는 최종 결과물 기준이며, 달라진 부분은 TECH_SPEC 12절에 적었다.

### A.1 제안한 모습
- 입력은 엑셀·CSV와 자연어 질문, 출력은 현황 요약, 주요 문제, 시각화, 후속 확인사항.
- 핵심은 사용자가 복잡한 그래프를 일일이 해석하지 않도록 **AI가 중요한 변화와 그 근거를 먼저 제시**하는 것.
- 같은 분석 엔진에 데이터만 바꿔 쓴다. 예: 안전관리자 "어느 구역에서 개선조치가 반복 지연되는가?", 품질관리자 "어느 공정의 불량 개선조치가 오래 걸리는가?", 시설관리자 "어떤 설비의 수리가 반복되는가?"
- 기획 단계의 가칭은 "Action Insight AI", 최종 이름은 Task Insight.

### A.2 넣어야 할 데이터
업무 내용을 표준화하는 것이 아니라 **업무 관리에 필요한 공통 항목만 정의**한다. 기획 단계 항목: ID, 분야, 업무 및 문제, 담당부서, 등록일, 기한, 상태 (구현에서는 발생일·완료일, 업무 유형, 반복 문제 식별 정보까지 정의하는 것을 권장).
계산하려던 것:
- 기한이 지난 미완료 업무는 몇 건인가?
- 담당부서별 처리율에 차이가 있는가?
- 어느 유형의 문제가 반복되는가?
- 처리기간이 늘어나고 있는가?
- 어떤 업무에 추가 확인이 필요한가?

'우선 확인'은 기한 초과, 반복 발생, 사용자 지정 중요도 같은 근거로 제시하고, **AI가 문제의 위험도를 자의적으로 확정하지 않는다.**

### A.3 시각화 원칙
차트를 나열하지 않고 **하나의 핵심 질문에서 시작**한다 (예: "이번 달에 가장 먼저 확인할 문제는?" → 부서별 기한 초과 막대 → 권장 확인사항). 이 정도만으로도 "엑셀 업로드 → 질문 → 그래프·설명 확인"의 완성된 흐름이 된다. 업무관리 데이터만으로는 지연의 원인을 알 수 없으므로 원인까지 단정하지 않는다.

### A.4 에이전트가 할 일
데이터를 LLM에 통째로 전달하지 않는다. **LLM이 분석 방법을 정하고, Python이 계산하고, 결과를 설명한다.** 처음부터 여러 에이전트를 만들지 않고 **단일 LLM + 4~5개 분석 도구 + 명시적 검증 로직**으로 시작한다 (예: `count_overdue_tasks`, `summarize_by_category`, `calculate_completion_rate`, `compare_periods`, `find_recurring_issues`).

### A.5 각자에게 남는 기술적 자산
| 해커톤 개발 결과 | 업무 활용 |
|---|---|
| CSV/DB 분석 파이프라인 | 안전점검, TBM, 개선조치 데이터 |
| 자연어 질문의 구조화 | 관리자의 자연어 데이터 조회 |
| 계산 도구 호출 | 개선조치 기한, 위험유형별 집계 |
| 데이터 근거 검증 | AI의 숫자 생성·사실 왜곡 방지 |
| 대시보드 시각화 | 사업장 현황, 보고서, PDCA 성과 |
| 보고서 생성 | 안전보건 월간 실적보고 |

핵심 자산은 **자연어 질의를 검증 가능한 데이터 조회와 계산으로 바꾸는 에이전트 구조**다.

### A.6 최종 제안 (당시)
- 주제: AI 기반 업무 현황 진단 및 개선 우선순위 분석 에이전트
- 핵심 고객: 데이터를 기반으로 업무 현황을 관리하는 실무자와 관리자
- 입력: 업무 관리 CSV/엑셀 + 자연어 질문
- 출력: 현황 요약, 문제 및 지연 분석, 그래프, 근거와 후속 확인사항
- 개발 범위: 5개 내외 분석 도구, 공통 데이터 구조 1개, 검증 가능한 질문 10~20개
- 단서: "어떤 엑셀이든 AI가 알아서 분석한다"는 약속은 하지 않는다. 지원하는 컬럼과 지표를 명확히 정해야 완성도와 신뢰성을 확보한다.
- 평가 아이디어: 엑셀 피벗이나 미리 구성한 대시보드와 비교해 사용자가 정보를 얻는 **단계 수와 정확성**을 평가한다 (결과: 정확성은 평가, 단계 수 정량 비교는 미수행).
