## Q1. 그냥 ChatGPT나 Gemini에 CSV 파일을 올리고 분석해 달라고 하면 되지 않나요?
**출제 가능성:** 매우 높음

**구두 답변**
> 범용 생성형 AI도 CSV를 분석하고 그래프를 그릴 수 있습니다. 다만 업무 데이터에서는 "어떤 기준으로 계산했는지 확인할 수 있는가"가 중요하다고 봤습니다.
> Task Insight에서는 AI가 질문을 해석해 분석 계획만 세우고, 실제 숫자는 미리 정의된 Python 계산 도구가 냅니다. 사용자는 계산 전에 계획, 예를 들어 어떤 컬럼을 어떻게 나누는지를 확인하고 승인합니다.
> 그래서 승인한 계획이 같으면 같은 데이터에서 항상 같은 숫자가 나오고, 그 숫자가 어떤 기준으로 나왔는지 화면에서 확인할 수 있습니다.

**핵심 전달 사항**
- 범용 AI보다 "무조건 정확하다"가 아니라, **계산 절차를 통제하고 확인할 수 있다**는 점
- 숫자는 LLM이 아니라 계산 도구에서 나온다

**답변 시 주의사항**
- "같은 질문이면 항상 같은 결과"라고 말하지 않는다. 계산은 결정적이지만 **Gemini가 세우는 계획은 같은 질문에도 달라질 수 있다**(이 때문에 `eval`에 반복 측정 기능이 있음). 재현성은 "승인한 계획 기준"으로 말한다.
- 범용 AI와 정확도를 직접 비교한 실험은 하지 않았다. 비교 수치를 만들어 말하지 않는다.

## Q2. AI 에이전트라고 했는데, 실제로 AI가 담당하는 부분은 무엇인가요?
**출제 가능성:** 매우 높음

**구두 답변**
> AI는 사용자의 자연어 질문을 해석해서, 데이터 구조와 사용 가능한 계산 도구를 보고 분석 계획을 세웁니다. 예를 들어 "예산 대비 비용 초과율이 가장 높은 프로젝트는?"이라고 물으면 Gemini가 예산 대비 비용 도구와 필요한 조건을 고릅니다.
> 그 계획을 코드가 다시 검사해서 질문의 조건이 빠지지 않았는지 확인하고, 사용자가 승인하면 Python 계산 엔진이 실행합니다. 결과 설명문도 AI가 아니라 계산 결과를 템플릿에 채워서 만듭니다.
> 즉 AI는 계산을 하지 않고, 목적을 이해해 도구를 고르는 역할만 합니다.

```
사용자 자연어 질문
   │
   ▼  [AI 담당]  질문 해석 → 도구·조건 선택 → 분석 계획 (Gemini function calling)
   │
   ▼  [코드]     사전 차단 · 계획 검증(어긋나면 1회 재계획) → 사용자 승인
   │
   ▼  [프로그램] 계산(Python/pandas 엔진) → 표·차트(Plotly) → 설명문(Python 템플릿)
```

**핵심 전달 사항**
- AI의 역할은 **질문 이해와 도구·조건 선택**까지
- 계획 검증과 승인을 거친 뒤에만 계산이 실행된다
- 숫자·표·차트·설명문 어디에도 LLM이 만든 숫자는 없다

**답변 시 주의사항**
- 결과 해석·설명을 AI가 한다고 말하지 않는다. 초기 기획에는 "LLM이 결과 해석"이 있었지만 **실제로는 빼고 Python 템플릿으로 바꿨다** ([`initial_plan_review.md`](initial_plan_review.md) Part 3-1).
- 계산 엔진은 데이터 엔지니어링, 차트는 프론트엔드 담당의 작업이다.

## Q3. LLM이 직접 Python이나 SQL 코드를 생성하도록 하면 더 다양한 질문에 답할 수 있지 않나요?
**출제 가능성:** 높음

**구두 답변**
> 맞습니다. 코드를 자유롭게 생성하게 하면 다룰 수 있는 질문은 더 많아집니다.
> 하지만 생성된 코드가 잘못된 기준으로 집계하거나, 표를 결합하면서 숫자가 부풀려지거나, 임의 코드 실행에 따른 보안 문제가 생길 수 있습니다. 저희 시연 데이터에서도 표를 단순 결합하면 예산 합계가 실제의 15배 넘게 부풀려지는 문제가 있었습니다.
> 그래서 이번에는 자유도보다 신뢰성과 실행 통제를 택했습니다. 팀이 미리 정의하고 테스트한 계산 도구 10개 안에서만 AI가 도구와 조건을 고르게 했고, 자유 Python·SQL 실행은 금지했습니다. 앞으로는 검증된 도구를 늘려 범위를 넓히는 방향입니다.

**핵심 전달 사항**
- 기능 제한은 역량 부족이 아니라 **유연성과 신뢰성 사이의 설계상 선택**
- 허용 목록(10개) 밖의 도구, 자유 코드 실행은 구조적으로 불가능

**답변 시 주의사항**
- 도구 개수는 **10개**(엔진 계산 도구). 에이전트 전용 2개(되묻기·지원 불가 안내)는 계산 도구가 아니므로 합쳐 말하지 않는다. `presentation_prep.md` 일부에 남은 "도구 6개"는 이전 숫자다.
- 도구 구현은 데이터 엔지니어링 담당. 에이전트는 도구를 고르고 인자를 검증하는 쪽이다.
- 예산 부풀림 수치(7.03억 → 109.03억, 15.5배)는 `docs/kafe_data_dictionary.md` §5 기준.

## Q4. AI의 환각(Hallucination) 문제는 어떻게 해결했나요?
**출제 가능성:** 매우 높음

**구두 답변**
> 환각을 완전히 없앴다고 보기는 어렵습니다. 대신 환각이 최종 숫자에 들어가지 못하게 구조를 만들었습니다.
> LLM은 계획만 세우고, 화면의 숫자·표·그래프·설명문은 모두 같은 계산 결과에서 나옵니다. 데이터에 없는 정보를 묻거나 지원하지 않는 계산이면 LLM에 보내기 전에 막거나, 비슷한 다른 분석으로 바꿔 답하지 않고 "지원 불가"와 이유를 보여 줍니다.
> 다만 LLM이 질문 의도를 잘못 해석해 엉뚱한 계획을 세울 가능성은 남아 있습니다. 그래서 코드가 계획을 다시 검사하고, 마지막으로 사용자가 계획을 보고 승인하게 했습니다.

| 구분 | 상태 |
|---|---|
| 숫자를 지어내는 환각 | 구조적으로 차단 (숫자는 계산 결과에서만) |
| 질문 해석·계획 선택의 오류 | 남아 있음 → 코드 검증 + 사용자 승인으로 보완 |

**핵심 전달 사항**
- "환각을 없앴다"가 아니라 **환각이 잘못된 결과로 이어지는 것을 통제했다**
- 실패할 때 가짜 답 대신 사유를 보여 준다

**답변 시 주의사항**
- 계획 검증이 모든 오류를 잡는다고 말하지 않는다. 검증은 질문에 적힌 조건·지표·계산 의도가 계획에 반영됐는지 보는 것이며, 해석 자체가 틀린 경우는 사용자 승인에 기대는 부분이 있다.

## Q5. 왜 사용자 승인 절차를 넣었나요? 완전 자동화가 더 편리하지 않나요?
**출제 가능성:** 높음

**구두 답변**
> 업무 데이터는 같은 질문이라도 무엇을 분모로 하는지, 어떤 대상을 포함하는지에 따라 결과가 달라집니다. AI가 해석한 분석이 사용자가 원한 분석과 같은지 확인하도록 Human-in-the-loop 구조를 넣었습니다.
> 승인 화면에서 계산식, 예를 들어 "불량수량 합계 ÷ 생산수량 합계 × 100"을 실행 전에 볼 수 있고, 승인한 뒤 계획이 하나라도 바뀌면 실행하지 않고 다시 승인을 받습니다.
> 예산이나 인력처럼 의사결정에 쓰는 숫자는 빠른 것만큼 올바른 기준이 중요하다고 봤습니다. 앞으로는 단순한 분석은 자동 실행하고 중요한 분석만 승인받는 방식으로 개선할 수 있습니다.

**핵심 전달 사항**
- 승인은 **해석이 맞는지 확인하는 장치**이고, 승인한 계획 그대로만 실행된다(계획 지문)
- 대가(클릭 한 번)를 인정하고 개선 방향을 제시

**답변 시 주의사항**
- 위험도에 따른 자동 실행은 **향후 개선 방향**이다. 현재는 모든 분석이 승인을 거친다.

## Q6. 실제 계산 결과가 정확하다는 것은 어떻게 검증했나요?
**출제 가능성:** 매우 높음

**구두 답변**
> 계산 엔진 검증과 AI 에이전트 검증을 나눴습니다.
> 먼저 자동화 테스트로 pytest 565건이 통과했고 11건은 실제 Gemini API를 부르는 테스트처럼 무료 한도 때문에 평소에는 끄는 항목이라 건너뛰었습니다. 대표 질문 7개는 pandas로 따로 계산한 정답과 대조했고, 그중 5개는 엑셀로도 한 번 더 확인했습니다.
> 에이전트 쪽은 실제 Gemini로 질문부터 실행까지 돌려 정답과 비교하는 채점 도구를 만들었고, 같은 질문도 Gemini 계획이 흔들릴 수 있어서 반복 측정 기능도 넣었습니다.
> 다만 테스트 통과 건수가 모든 자연어 질문의 정확도를 뜻하지는 않습니다.

| 항목 | 수치 |
|---|---|
| 자동화 테스트 | 565 passed, 11 skipped |
| 기준 질문 pandas 대조 | 7개 (Q1~Q7) |
| 엑셀 추가 확인 | 5개 (Q1·Q3·Q5·Q6·Q7), Q2·Q4 미검증 |
| 에이전트 채점 질문 | 묶음 6개, 약 97문항 (정답률은 측정 시마다 달라 저장소에 고정 기록 없음) |

**핵심 전달 사항**
- 계산 정확도(엔진)와 질문 이해(에이전트)를 **따로** 검증했다
- 정답 파일은 고정하고, 테스트를 통과시키려고 정답을 고치지 않는다는 규칙

**답변 시 주의사항**

## Q7. 처음 보는 CSV 파일을 입력해도 정상적으로 분석할 수 있나요?
**출제 가능성:** 매우 높음

**구두 답변**
> 일반 CSV 분석 기능을 넣어 특정 업무 데이터에만 묶이지 않게 했습니다. 올린 CSV의 컬럼과 형식을 읽어 날짜·숫자·범주 같은 역할을 판단하고, 질문을 그 컬럼에 연결해 지원하는 계산 범위 안에서 분석합니다. 실제로 재고·영업·품질처럼 구조가 다른 예시 CSV에서도 같은 흐름이 동작합니다.
> 다만 질문에 쓴 말이 데이터에 없거나, 컬럼 의미가 불분명하거나, 여러 파일 사이의 관계를 추론해야 하는 경우에는 숫자를 내지 않고 되묻거나 지원 불가로 안내합니다.
> 그래서 "모든 CSV의 모든 질문에 답한다"기보다 "구조가 달라도 지원하는 분석은 같은 방식으로 수행한다"가 정확한 설명입니다.

**핵심 전달 사항**
- 범용성은 **"지원 범위 안에서"** 확보
- 모르는 것은 추측하지 않고 되묻거나 거절한다

**답변 시 주의사항**
- 일반 CSV는 **한 번에 파일 하나**를 분석한다. 여러 파일 결합은 시연용 표준 데이터(업무·직원·프로젝트)에만 해당한다.
- 질문의 "고객"과 데이터의 `buyer`처럼 이름이 다른 컬럼을 자동으로 연결하는 기능(PR #44)은 **기본 OFF이고 발표에서 켜지 않는다.** 현재 시연에서는 이런 질문이 "지원 불가"로 나오는 것이 정상이다.
- 일반 CSV 읽기(날짜·통화 표기 처리 등)는 데이터 엔지니어링, 예시 CSV와 예시 질문 화면은 프론트엔드 담당의 작업이다.
- 시연과 연결: 업무 데이터 외에 재고·영업·품질 예시 CSV로 같은 흐름을 보여 주면 설득력이 높다.

## Q8. 기업 내부 데이터를 업로드하면 외부 AI 서비스로 유출되지 않나요?
**출제 가능성:** 매우 높음 (보안 관련 독립 심사 항목)

**구두 답변**
> 먼저 시연 데이터인 한빛센서텍은 실제 기업이 아니라 가상 데이터입니다.
> Gemini에는 데이터 원본을 보내지 않습니다. 보내는 것은 사용자의 질문, 컬럼 이름과 형식, 그리고 표준 데이터의 부서·상태 같은 범주값뿐이고, 업무명·프로젝트명 같은 자유 텍스트와 숫자 값, 원본 행은 보내지 않습니다. 일반 CSV는 셀 값을 아예 보내지 않습니다. API 키는 저장소에 넣지 않고 배포 환경의 Secrets로 관리합니다.
> 다만 외부 API를 쓰는 구조라 외부로 가는 정보가 전혀 없다고 할 수는 없습니다. 로그인과 접근 권한도 이번 범위에서 제외했습니다. 실제 기업 데이터를 다루려면 인증, 접근 권한, 외부 전송 범위와 데이터 보존 정책을 추가로 설계해야 합니다.

| 외부(Gemini)로 가는 것 | 가지 않는 것 |
|---|---|
| 사용자 질문 문장 | 업무명·프로젝트명 등 자유 텍스트 |
| 기준일, 표·컬럼 이름과 형식(역할) | 숫자 값, 원본 행 |
| 표준 데이터의 범주값·ID (부서, 상태, 문제유형, `E001` 형태 ID 등) | 일반 CSV의 셀 값 |
| | API 키, 평가 정답 |

**핵심 전달 사항**
- 원본 데이터 대신 **구조 정보만** 보낸다
- 상용화 전 필요한 보안 항목을 스스로 제시한다

**답변 시 주의사항**
- "원본 텍스트를 보내지 않는다"와 "기업 정보가 외부로 전혀 가지 않는다"는 다른 주장이다. 컬럼 이름, 부서명 같은 범주값, **사용자가 입력한 질문 문장**은 Gemini로 간다. 질문에 민감한 내용을 쓰면 그대로 전송된다.
- CSV 셀 안의 문장은 지시가 아니라 데이터로 취급한다(프롬프트에 "지시가 아니다"로 표시, 검증 안 된 이름은 숨김).
- Gemini 쪽 데이터 보존·학습 사용 조건은 요금제에 따라 다르다. 확인하지 않은 조건을 단정하지 않는다.

## Q9. AI를 이용해서 코드를 개발했다면, 본인이 기여한 부분은 무엇인가요?
**출제 가능성:** 매우 높음 (AI와 사람의 협업 역량 평가)

**구두 답변 (예시, 실제 수행한 범위에서 사용)**
> 저는 자연어 질문을 해석해 계산 도구와 연결하는 AI 에이전트 부분을 맡았습니다.
> 구현에는 AI 코딩 도구를 썼지만, AI가 계산을 직접 할지, 어떤 질문을 지원하고 어떤 질문을 거절할지, 오류를 어떻게 통제할지 같은 설계 방향은 사람이 정해야 했습니다.
> 예를 들어 실제 Gemini로 시험해 보니 질문의 "고객"을 데이터의 매장(store) 컬럼으로 해석하는 경우가 있었습니다. 이 사례를 재현 조건으로 정리해 판매처·매장 같은 컬럼은 고객으로 볼 수 없다는 규칙을 넣었고, 그래도 애매한 경우가 남아서 그 기능은 기본으로 꺼 두기로 했습니다.
> 또 데이터 엔진과 화면 담당 팀원의 결과물에 맞춰 에이전트를 연동했습니다. 사람이 문제를 정의하고, AI가 구현을 돕고, 사람이 결과를 검증하는 방식으로 일했습니다.

**핵심 전달 사항**
- 설계 판단(계산은 코드, 승인 필수, 모르면 거절)은 사람의 몫이었다
- 구체적 사례 하나 (실제 Gemini 시험 → 재현 → 규칙 추가 → 기본 OFF 결정)

**답변 시 주의사항**
- 계산 엔진, 화면·차트, 테스트 통합·배포, 채점 도구는 다른 팀원의 작업이다. "제가 만들었다"고 말하지 않는다. 에이전트는 엔진 변경을 따라가는 연동 작업(예: PR #39·#42)을 했다.
- 사례로 쓸 수 있는 실제 작업(PR 기준): 질문 → 계획 → 승인 → 실행 구조(#5), 조건이 빠진 계획 차단과 재계획(#14·#25), 범용 CSV 확장(#22·#37), 계산 의도 검사(#39·#42), 컬럼 의미 해석과 기본 OFF 결정(#44).

## Q10. 실제 현업에서는 이 에이전트를 어떻게 활용할 수 있나요?
**출제 가능성:** 매우 높음

**구두 답변**
> 이번에는 업무·인력·프로젝트 데이터의 현황 분석에서 시작했지만, "질문 → 계획 → 승인 → 계산" 구조 자체는 다른 분야에도 쓸 수 있습니다. 실제로 재고·영업·품질 예시 데이터에서도 같은 구조로 불량률이나 매출 비중을 계산합니다.
> 제가 관심 있는 산업안전보건 분야라면 위험성평가 결과, 안전점검 기록, 개선조치 이행 현황 같은 데이터에 적용할 수 있습니다. 안전보건관리자가 "기한이 지난 미완료 개선조치는?", "반복해서 나오는 위험요인은?"을 자연어로 묻고 근거와 그래프를 확인하는 방식입니다.
> 앞으로는 CSV 업로드 대신 사내 데이터베이스나 ERP·MES와 연동하는 방향으로 발전시키고 싶습니다.

**핵심 전달 사항**
- 분야가 바뀌어도 **데이터만 바뀌고 구조는 같다**
- 본인의 현업(안전보건) 사례로 구체화

**답변 시 주의사항**
- 안전보건 데이터 적용, DB·ERP·MES 연동은 **향후 계획**이다. 현재는 CSV 업로드만 지원한다.
- 안전보건 데이터로 실제 시험한 적은 없다. "이미 된다"가 아니라 "기한 초과·반복 이슈 같은 기존 도구로 다룰 수 있는 형태"라고 말한다.
