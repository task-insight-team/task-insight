## 4. 인시(MH) 정의

| 개념 | 위치 | 의미 |
|---|---|---|
| 계획 MH | `tasks.planned_mh` | 업무 하나를 끝내는 데 필요하다고 본 **총 공수** |
| 실적 MH | `tasks.actual_mh` | 업무 시작부터 기준일까지 **누적된 공수**. 기간 정보가 없다 |
| 주당 가용시간 | `employees.weekly_capacity_mh` | 직원이 **한 주에** 프로젝트에 쓸 수 있는 시간. 저량(stock)이 아니라 유량(flow/주)이다 |

**⚠️ `actual_mh`와 `weekly_capacity_mh`는 같은 개념이 아니다.**
`actual_mh`는 업무 기간 전체에 걸친 누적값이고, 어느 주에 몇 시간을 썼는지는 알 수 없다.
그래서 "직원 E0xx의 실적 MH 합계(예: 300MH) > 주당 가용시간(36MH)"을 과부하의 근거로 쓰면 **잘못**이다.
기간을 감안해도 업무 기간에 균등하게 투입했다는 가정이 필요하다. 이 데이터로 할 수 있는 것은 **추정**뿐이다.

### 초과 투입 판정 (정상 vs 초과)

- 완료 업무: `actual_mh > planned_mh × 1.2` → **초과 투입**. `≤ 1.2`는 정상 편차로 본다(생성 시 0.85~1.12).
- 미완료 업무: `actual_mh > planned_mh` → 아직 끝나지 않았는데 계획을 넘은 **초과 진행**.
- 프로젝트 MH 초과량(평가 Q3): `Σ max(actual_mh − planned_mh, 0)`.
  미완료 업무의 '남은 계획 MH'가 다른 업무의 초과분을 상쇄하지 않도록 업무 단위 초과분만 더한다.

### (제안) 주차별 과부하 분석용 확장 구조 — MVP 미포함

주차별 과부하를 정확히 분석하려면 **시간 기록(timesheet) 팩트 테이블**이 필요하다.

```
timesheets.csv
  entry_id        PK
  employee_id     FK → employees
  task_id         FK → tasks      (NULL = 비프로젝트 정례업무)
  week_start      date (월요일)
  mh              float ≥ 0
제약: Σ mh (task_id 기준) = tasks.actual_mh
      주별 Σ mh (employee_id, week_start) 와 weekly_capacity_mh 비교 → 과부하 주차 판정
```

함께 두면 좋은 보조 테이블:
- `employee_absences`(휴가·교육): 주별 가용시간 차감
- `calendar_weeks`(주차 차원): 공휴일 반영
- `task_baselines`(기한 변경 이력): 일정 변경 분석

MVP에는 넣지 않았다. `validate_dataset.py`의 `[참고]` 항목은 '첫 업무 시작~기준일 주수 × 주당 가용시간' 대비 누적 MH 비율만 보여 준다.
기준일 시점에 최대 0.54, 평균 0.12다. 프로젝트 업무가 근무시간의 일부일 뿐이라는 가정과 맞는다.

## 5. 예산·비용 집계 기준

```
업무 실적 인건비(추정) = tasks.actual_mh × employees.hourly_labor_cost (담당자 기준)
업무 실적 총비용        = 업무 실적 인건비 + tasks.actual_nonlabor_cost
프로젝트 실적 비용      = Σ 업무 실적 총비용 (project_id 기준)
프로젝트 비용 초과율    = 프로젝트 실적 비용 / projects.budget − 1
```

1. **예산은 `projects.budget`에만 있다.** 업무 테이블에는 예산을 나눠 저장하지 않는다.
2. **이중 계산 금지**: `tasks`와 `projects`를 조인한 뒤 `budget`을 합하면 프로젝트당 업무 수만큼 중복된다.
   이 데이터에서는 실제 예산 합계 7.03억 원이 109.03억 원(15.5배)으로 부풀려진다. 예산은 프로젝트 단위에서 한 번만 쓴다.
   비용은 업무 단위로 계산한 뒤 프로젝트로 합한다.
3. `tasks ⋈ employees` 조인은 다대일(many-to-one)이어야 한다. 조인 뒤 행 수가 150으로 유지되는지 검증한다.
4. 인건비는 **추정액**이다. 현재 직원 단가를 소급 적용하고, 단가 변동 이력은 없다.
   담당자 누락 업무 4건은 모두 미착수(실적 MH 0)라 인건비 계산에 영향이 없다.
5. 비인건비는 실제 지출 성격이다. 인건비와 따로 집계하고 따로 보고할 수 있다.
6. 진행중 프로젝트의 실적은 **기준일 누적**이다. 총예산과 비교하면 '이미 소진한 비율'이 된다. 완료 시점 예측(EAC)이 아니다.
7. 예산 산정 방식(생성 로직): `(Σ planned_mh × 담당자 단가 + Σ planned_nonlabor_cost) × 예비율`을 백만 원 단위로 반올림했다.
   예비율은 기본 1.08~1.18, P01 1.02, P02 1.00이다.

## 8. 재현 및 검증

```bash
python generate_dataset.py      # data/, evaluation/, SCENARIOS.md 재생성
python validate_dataset.py      # 정합성 + 정답 재계산 + 재현성(SHA-256) 검사 → validation_report.txt
```

- 난수는 Python 표준 `random.Random(20261119)` 하나만 쓴다. numpy는 쓰지 않고, set 순회 순서에도 의존하지 않는다.
- 생성 스크립트는 정답을 다시 계산한다. 의도한 시나리오(Q3=P05, Q4=P01, Q7=E032, 1인당 미완료 최대 부서=품질)가 성립하지 않으면 `assert`로 멈춘다.
- 평가 정답(`evaluation_answers.json`)은 **고정본**이다. 생성 로직을 바꾸면 검증의 재현성 검사가 실패하므로 바로 알 수 있다.
