# 발표 준비 세팅 (Claude 작업용)

> 발표 내용을 정리할 때 Claude에게 시킬 작업과 쓸 스킬 조합. 앱 코드가 아니라 **발표 자료 작성용**이다.
> 정답 파일(`tests/fixtures/kafe/`, `SCENARIOS.md`)은 Claude Code 대화에서 숫자 대조용으로 읽는 것은 괜찮지만, **앱의 LLM 프롬프트에는 절대 넣지 않는다** (CLAUDE.md 규칙).

## 1. 추천 조합

| 용도 | 쓸 것 | 이유 |
|---|---|---|
| 발표 숫자 검증 | `data:validate-data` | 슬라이드에 쓸 수치(Q1~Q7)를 `data/kafe/*.csv`에서 다시 계산해 정답표와 대조 |
| 근거 숫자 보강 | `data:analyze`, `data:explore-data` | 질의응답 대비용 보조 수치(프로젝트별 초과, 부서별 편중 등) 빠르게 확인 |
| 슬라이드용 차트 | `data:create-viz` (또는 앱 화면 캡처) | 발표 모드 화면을 캡처하면 "차트 값 = 표 값" 원칙이 그대로 보임. 별도 차트가 필요할 때만 사용 |
| 발표 자료 | `anthropic-skills:pptx` | 최종 .pptx 생성 (슬라이드 형식을 지정하면 그에 맞춤) |
| 대본·예상질문 | 기본 대화 + `anthropic-skills:docs` | 5분 대본, Q&A 카드 |

쓰지 않는 것: `sql-queries`, `write-query`, `build-dashboard`, 웨어하우스 MCP(Snowflake·BigQuery 등), `statistical-analysis`.
이유: 이 프로젝트는 CSV + 허용된 도구 10개만 쓰고(자유 SQL 금지), 대시보드는 Streamlit이 이미 있다.

## 2. 발표 뼈대 (레포 근거)

1. **도입(배경, 슬라이드 3장, 약 1분 40초)**: 시연 전에 세계 상황에서 출발한다.
   - 군함 건조 2년 새 50% 급증: 건조 가치 1,220억 달러(직전 818억), 전투함 147만t(직전 95.9만t), 중국 63.6만t·미국 27.1만t (사이언스모니터 2026-11-03 기사, 톤수는 산출 지표이고 집계 기준은 비공개)
   - 물량이 늘면 병목은 공정에서 생긴다: 미국 조선소 투입 공수 13M → 70M man-hours(약 5.4배), 중국 후루다오 핵잠수함 생산 능력 2배, 러시아 낮은 생산 속도·부품 공급 차질 (Euronaval 영문 보고서 PDF). **병목이라는 해석은 발표팀의 정리**이고 기사에는 병목 언급이 없다
   - 같은 질문의 모양: 기한 초과 15건, 품질 부서 18건(1인당 2.57), P05 +370 MH, P01 +30.72%. **조선 데이터로는 검증하지 않았고** 가상 제조기업 데이터다
2. **문제**: 다중 CSV를 조인하면 수치가 부풀려진다. 예산 합계 7.03억 → 109.03억 원(15.5배) (`kafe_data_dictionary.md` §5)
3. **해법**: 질문 → 계획 → **사용자 승인** → 도구 실행 → 표·차트·근거. LLM은 도구와 인자만 고르고 숫자는 Python이 계산
4. **가드레일**: 허용 도구 외 실행 금지 / 승인 전 실행 금지 / 오류 시 가짜 답 대신 "실패" 표시 / 자유 텍스트 컬럼은 프롬프트 제외 / 기준일 입력 필수
5. **시연 (기준일 2026-11-19)**: 아래 정답표 질문을 앱에서 실행
6. **검증**: pytest 565 통과·11 건너뜀 (2026-11-25 실행), 정답 7개를 pandas 별도 계산으로 교차 확인, Q1·Q3·Q5·Q6·Q7은 엑셀 확인
7. **한계(솔직하게)**: 한 계획 최대 4단계·앞 결과에 의존하는 질문 미지원, Q2·Q4는 엑셀 미검증, 인건비는 추정액, 주차별 과부하는 timesheet 없어 미포함
8. **확장(마무리 근처)**: 조선 공정관리를 첫 예시로, 생산·품질, 안전보건(EHS), 프로젝트·경영으로 확장. 실제 적용에는 ERP·MES 연동과 보안·권한 설계가 필요하며 현재 구현된 기능이 아니다 (.pptx 14번 슬라이드)

## 6. 예상 질문 11개와 답변

> 모든 답은 저장소에서 확인되는 사실만 썼다. 각 답은 30초 안에 말할 수 있는 길이로 쓰고, "근거"에는 질문이 더 깊어질 때 열어 볼 위치를 적었다. 채점 점수처럼 아직 측정하지 않은 값은 지어내지 않고 "측정 전"이라고 답한다.

### Q1. LLM이 숫자를 지어내지 않는다는 것을 어떻게 보장하나요?
**답:** 보장하는 방식이 지시가 아니라 구조입니다. LLM은 도구 이름과 조건만 고르고, 계산은 `engine.run_tool`만 합니다. 결과 설명도 LLM이 아니라 Python 템플릿이 `ToolResult` 값으로만 만들기 때문에, 설명문에 숫자를 지어 넣는 것이 구조적으로 불가능합니다.
**근거:** `agent/explain.py`, `engine/registry.py`, README 핵심 원칙 1.
**주의:** 설명문이 덜 자연스럽고 여러 결과를 엮은 해석은 못 한다는 대가를 함께 말한다.

### Q2. 승인 단계가 번거롭지 않나요? 왜 넣었나요?
**답:** 처음 기획에는 없었고 개발하면서 추가했습니다. Gemini가 질문의 조건(부서·기간)을 빠뜨리거나 비슷한 다른 지표를 고르는 일이 반복됐기 때문입니다. 사용자가 계산식을 실행 전에 보고, 승인 후 인자가 하나라도 바뀌면 다시 승인을 받습니다. 대가는 클릭 한 번과 호출 지연입니다.
**근거:** `docs/initial_plan_review.md` Discussion 2, `agent/executor.py`(`plan_hash`).

### Q3. 여러 CSV를 합칠 때 수치가 부풀려지는 문제는 어떻게 막았나요?
**답:** 예산을 업무 행에 붙이지 않고 프로젝트 표에서 프로젝트당 한 번만 씁니다. 업무 → 직원·프로젝트는 다대일로 결합하고, 결합 후 행 수가 업무 행 수(150)와 다르면 결합 결과를 쓰지 않습니다. 직원·프로젝트 표에 ID 중복이 있어도 결합하지 않습니다. 예산을 붙여 합하면 7.03억이 109.03억(15.5배)이 됩니다.
**근거:** `docs/data_rules.md` 3절, `tests/test_join.py`.

### Q4. 어떤 엑셀이든 분석할 수 있나요?
**답:** 아니요, 그렇게 약속하지 않았습니다. 일반 CSV도 분석하지만 지원하는 도구는 10개이고, 데이터에 없는 컬럼이나 지원하지 않는 계산은 다른 분석으로 바꿔 답하지 않고 숫자 없이 "지원 불가"로 끝냅니다. 질문 용어와 컬럼 이름이 다를 때 후보를 찾는 컬럼 의미 해석은 정확도를 위해 기본 OFF로 두었고 발표에서도 켜지 않습니다.
**근거:** `docs/data_rules.md` 6절, `eval/README.md`(`refuse` 묶음), `agent/guard.py`(`TI_COLUMN_HINTS`).

### Q5. 정확도는 어떻게 검증했나요?
**답:** 세 겹입니다. 고정 정답 테스트(kafe 질문 7개, sample.csv 5개)와 pytest 565개 통과, 정답 7개를 CSV에서 pandas로 따로 다시 계산해 모두 일치했습니다. 엑셀로는 Q1·Q3·Q5·Q6·Q7을 확인했고 Q2·Q4는 결합이 필요해 아직 엑셀 확인이 없습니다. 에이전트가 맞는 도구를 고르는지는 약 97문항 6개 묶음으로 채점하는데, 점수는 측정 전입니다.
**근거:** `docs/answer_key.md`, `eval/README.md`, FINAL_CHECKLIST.
**주의:** 채점 점수를 말하기 전에 `eval --set core`를 돌려 값을 확인하고, 값이 없으면 "측정 전"이라고 답한다.

### Q6. CSV 안에 악성 지시문이 들어 있으면 어떻게 되나요?
**답:** CSV 내용은 지시가 아니라 데이터로 취급합니다. 업무명·프로젝트명 같은 자유 텍스트는 LLM에 보내지 않고, 컬럼 이름과 범주값은 짧은 라벨만 보내며 "무시", "삭제", "ignore" 같은 지시문 표현이 있으면 제외합니다. 그리고 LLM이 무엇을 요청하든 실행되는 것은 허용 목록의 도구 10개뿐입니다. 주입 샘플 `data/errors/injection.csv`로 확인합니다.
**근거:** `agent/context.py`(`safe_label`), `tests/test_safety.py`.

### Q7. Gemini가 느리거나 실패하면 어떻게 되나요?
**답:** 가짜 답을 만들지 않고 "실패"로 표시합니다. 무료 한도 초과(429)는 채점에서 오답으로 세지 않고 재시도하며, 그래도 안 되면 "측정 못 함"으로 기록합니다. 발표에서는 미리 앱을 깨워 두고 장애에 대비한 백업 캡처를 준비했습니다.
**근거:** README 핵심 원칙 5, `eval/README.md`, `agent/README.md`(모델 가용성).

### Q8. 올린 데이터와 개인정보는 어떻게 다루나요?
**답:** 로그인과 저장 기능을 만들지 않아서 분석 결과를 저장하지 않습니다. 업로드 파일은 서버 메모리 캐시(최대 4건)에 한시적으로 남을 수 있습니다. LLM에 보내는 것은 컬럼 이름, 범주값, ID 목록, 기준일이고, 숫자 값과 자유 텍스트는 보내지 않습니다. 시연 데이터는 합성 데이터라 개인정보가 없습니다.
**근거:** `agent/context.py` 머리말, PRD 9절(L-02, L-07).
**주의:** ID 목록(예: 직원 ID)은 LLM에 전달된다는 점을 숨기지 않는다.

### Q9. 로그인·저장을 왜 만들지 않았고, 아직 못 하는 것은 무엇인가요?
**답:** 과제 Step 1과 Step 3(계획 → 승인 → 실행 → 기록)에 집중하려고 Step 2를 의도적으로 제외했습니다. 못 하는 것은 분명합니다. 한 계획은 독립인 단계 4개까지이고 앞 결과에 따라 달라지는 질문은 지원하지 않으며, 월 단위 비교만 되고, 파일을 올리자마자 문제를 알려 주는 기능이 없습니다. 인건비는 현재 단가를 소급한 추정이고 비용 초과율은 기준일 누적값입니다.
**근거:** PRD 3.2·6.3절, `docs/data_rules.md` 6절, 검증과 한계 슬라이드.

### Q10. 엑셀 피벗이나 다른 BI 도구보다 나은 점이 있나요? 비교해 봤나요?
**답:** 정량 비교는 하지 못했습니다. 처음 계획에는 "정보를 얻는 단계 수와 정확성"을 비교하는 것이 있었는데, 정확성은 정답 7개를 엑셀 풀이와 함께 기록했지만 단계 수는 측정하지 않았습니다. 대신 이 도구의 차별점은 세 가지입니다. 조인 부풀림을 막는 결합 규칙, 계산식을 실행 전에 확인하는 승인, 지원하지 않는 질문을 솔직히 거절하는 점입니다.
**근거:** `docs/initial_plan_review.md` Part 2·3, `docs/answer_key.md`(엑셀 풀이).
**주의:** "더 빠르다"처럼 측정하지 않은 주장은 하지 않는다.

### Q11. 왜 조선(군함) 이야기로 시작했나요? 조선 데이터로 검증했나요?
**답:** 건조 물량이 급증하면 공수, 공급, 일정이 동시에 움직이는 공정관리 문제가 커진다는 점에서 시작했습니다. 기사는 급증 수치를, 영문 보고서는 미국의 공수 5.4배 확대 계획 같은 병목의 단서를 줍니다. 다만 병목이라는 해석은 저희의 정리입니다. 그리고 조선 데이터로는 검증하지 않았습니다. 같은 분석 구조(기한 초과, 부서별 편중, 공수 초과, 비용 초과)가 가상 제조기업 데이터에서 정답과 일치한다는 것까지만 확인했고, 실제 적용에는 데이터 연동과 보안 설계가 필요합니다.
**근거:** 슬라이드 도입 3장, `docs/answer_key.md`, Euronaval 영문 보고서(PDF), 사이언스모니터 기사(2026-11-03).
**주의:** "조선소의 병목을 해결한다"고 말하지 않는다. 기사의 톤수는 산출 지표이고 집계 기준이 공개되지 않았다는 한계도 함께 말한다. 방산 조선 데이터는 보안 문제가 있어 공개 가능한 민수·가상 데이터로 시작한다고 답한다.

### 답변 원칙
